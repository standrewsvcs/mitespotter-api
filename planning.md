## Dataset Export Format

The format to which the dataset is exported for training. We use the COCO format for compatibility with a majority of modern object detection software. The COCO format is a single JSON file linking to images.

https://cocodataset.org/#format-data

```json
{
    "info": info,
    "images": [image],
    "annotations": [annotation],
    "categories": [category]
    "licenses": [license],
}

info {
    "year": int,
    "version": str,
    "description": str,
    "contributor": str,
    "url": str,
    "date_created": datetime,
}

image {
    "id": int,
    "width": int,
    "height": int,
    "file_name": str,
    "license": int,
    "flickr_url": str,
    "coco_url": str,
    "date_captured": datetime,
}

license {
    "id": int,
    "name": str,
    "url": str,
}

annotation {
    "id": int,
    "image_id": int,
    "category_id": int,
    "segmentation": RLE or [polygon],
    "area": float,
    "bbox": [x,y,width,height],
    "iscrowd": 0 or 1,
}

category {
    "id": int,
    "name": str,
    "supercategory": str,
}
```

### Archive Directory Layout

Used for both versions and snapshots; only the root directory name differs.
A version is named `mitespotter_v1.0.0/`, a snapshot `mitespotter_2026-08-09/`,
and a snapshot additionally carries `MANIFEST.json` (see
[Version vs. Snapshot](#version-vs-snapshot)). Image files are named by their
full sha256 (abbreviated below), which is also the image's public identifier.

The web application cannot support massive concurrent writes to a single JSON file. Instead, it holds them in a database  and exports to COCO regularly.

**NB**: This SQL describes the schema only. The real implementation is SQLAlchemy models (advanced-alchemy bases) in `models.py`, and the database is only ever changed through Alembic migrations (see [Migrations](#migrations)). API payloads are msgspec structs and Litestar DTOs generated from the models.

Note also that the license is hardcoded at export and has no live source.

### Migrations

- Schema changes are made only through Alembic, driven by advanced-alchemy's Litestar CLI: `uv run litestar --app mitespotter_api.app:app database make-migrations` and `... database upgrade`.
- The app never runs `create_all`. Startup does not touch the schema.
- The first revision creates the `CITEXT` extension and the `categories` table, and seeds categories 1 and 2. Later revisions add the remaining tables.
- Every revision must downgrade cleanly; the test suite runs `upgrade head` and `downgrade base` against a real Postgres.
- Autogenerate output is a draft to review. It does not detect CHECK constraints added to or removed from existing tables: write those by hand. A test builds one database with `create_all` and one with `upgrade head` and compares their catalogs, so a forgotten constraint fails the build.

### Image Status

There is no status column. Status is derived; only non-deleted images and annotations count. The latest of an image's `complete`, `verify` and `reject` events decides it:

| Latest of `complete` / `verify` / `reject` | Annotations | Status      |
| ------------------------------------------ | ----------- | ----------- |
| `verify`                                   | any         | Verified    |
| `complete`                                 | any         | Annotated   |
| `reject`                                   | any         | Rejected (stays Rejected while being re-annotated, until completed again) |
| none                                       | ≥ 1         | In Progress |
| none                                       | 0           | Uploaded    |

## 2026 Implementation Plan

Dual repository: `mitespotter` (frontend) and `mitespotter-api` (backend). Room for future admin frontend.

Stack: **Litestar + advanced-alchemy (SQLAlchemy 2, async) + Alembic + Postgres 16 + psycopg3 + msgspec**, frontend **React/Vite/Tailwind/Zustand**. See [Deployment](#deployment) for where each piece runs.

Annotation concept: **Upload** > **Annotate** > **Complete** > **Verify** | **Reject**.

- **Upload.** An image is uploaded and added to the gallery.
- **Annotate**. Users draw bounding boxes around all mites they find.
- **Complete**. A user is satisfied that all varroa mites are labelled and presses "Finish Annotation."
- **Verify.** A user who is not the uploader and has no annotations on the image (live or deleted) reviews it. They choose either "Confirm annotations are correct" or "Flag annotations for further review" to reject it.
- **Reject**. A rejected image gains a "rejected" status so it can be highlighted as near completion, but it behaves exactly like a newly "uploaded" image. It is re-annotated and re-submitted for verification.

Only verified images are exported in the dataset.

Once an image is verified, annotations cannot be added. However, users will eventually be able to report verified images as wrong or incomplete.

A **registered** user has a verified email and a sign-in method (password or Google). Only registered users can make edits of any kind (uploads, annotations, reviews, reports). Registration is independent of `anonymous`, which only hides the user's name from the public.

Duplicate image uploads are rejected with 409.

#### Accounts & Authentication

You need an account to contribute, for credit; tick `anonymous` to hide your name publicly. Sign in with email and password, or with Google. User-facing text follows [STYLE.md](./STYLE.md) and lives in `messages.toml`.

- **`Auth`.** Holding an `Auth` means being signed in. Only a successful sign-in creates one: session cookie, password, emailed code or Google. It carries `user` and its behaviour: `logout()`, `logout_everywhere()`, `change_password()`, `link_google()`, `require_registered()`. Handlers that need a signed-in user take an `auth: Auth` dependency; anything else gets 401. There is no auth service.
- **Session cookie.** A random session id in a `Secure`, `HttpOnly`, `SameSite=Lax` cookie on `/api`; only its sha256 is stored, in `user_sessions`. Signing out deletes the row. CSRF protection is on.
- **Registration.** Email typed twice, password once with a show/hide toggle, optional name, `anonymous`.
  - Your password matches the account at that address: you're signed in.
  - Otherwise: "We've emailed you your verification code." Entering it creates the account, or sets the new password on the existing one; verifies the email; signs out other sessions; signs you in.
  - Accounts exist only once their code is entered, so every email account is verified, and a new address looks the same as an existing one.
- **Google.** OpenID Connect with PKCE, `state` and `nonce`; name and email from Google's ID token.
  - Known Google account: you're signed in.
  - Google-verified email matching an account: linked and signed in; the account keeps its password.
  - Otherwise: a new account, verified, without a password.
- **Usernames.** Generated from the id: an adjective and a noun picked by a generator seeded with the id (`nimble longstepper`); the lowest free number is appended if the pair is taken (`buzzy finder 1`).
- **Sign in.** "Incorrect email or password." for any failure. Unknown emails are checked against a dummy hash. Outdated hashes are upgraded on sign-in. AI models never use passwords.
- **Codes.** 6 digits, emailed through Resend, valid 15 minutes, 5 attempts, single use, one open code per address and purpose, at most one email a minute. Stored as an HMAC keyed with the secret key, in `email_codes`, with the password and details they apply.
- **Recovery, one screen.** Enter your email and a new password: "We've emailed you your recovery code." Enter the code: you're signed in with the new password and your other sessions end. Unknown addresses get the same response and no email.
- **Change password.** Needs your current password; ends your other sessions.
- **Rate limits.** Every `/api/auth` request, per client IP (`CF-Connecting-IP`).
- **Roles.** Admins (sprint 3+) and AI models are independent: a user may be either, both or neither, so roles are never a single enum. AI models authenticate with API keys (sprint 3+).

#### Reports & Deletion

A report flags one image for attention. Images stay visible and usable until acted on.

Until sprint 3 or later, administration (acting on and resolving reports) is done by the development team via direct database access, in service of practicality.

- **Reporting.** Registered users only (registered users who chose to be `anonymous` included). One open report per user per image (`uq_reports_open`). A reporter can resolve their own report at any time, withdrawing it, and can create new ones. Deleted images cannot be reported.
- **Reasons.** `not_a_board`, `duplicate`, `unusable_quality`, `personal_or_inappropriate`, `incorrect_annotations`, `other`. Notes are required for `other` and optional otherwise.
- **Incorrect annotations.** `incorrect_annotations` is for verified images only (enforced in the service). Disagreement with an unverified image's annotations goes through reject.
- **Uploader deletion.** An uploader can delete their own image directly only while it is unverified and has no annotations from other users. Otherwise they report it.
- **Soft deletion.** Deleting sets `images.deleted_at` and writes a `delete` image event. Exports exclude images where `deleted_at IS NOT NULL`.

#### Version vs. Snapshot

A **version** is a manually marked and numbered export of the dataset which is made immutable and publicly available via Zenodo, with a DOI.

A **snapshot** is an automatically generated export of the dataset which is temporary and used for internal training. It is marked by date, not version. It always includes the following additional manifest:

```json
{
    "DISCLAIMER": "The following is an internal-only snapshot of the mitespotter.org dataset. It should not be cited or distributed. For the official versions, see https://mitespotter.org/download",
    "snapshot": "2026-08-09",
    "max_image_event_id": 1109,
    "max_annotation_event_id": 3832,
    "image_count": 120,
    "annotation_count": 1904
}
```

#### Dataset Split

Training/validation/test split is based on `uploader_id` so that every image from one contributor lands in the same split. Images of the same hive or drop board are highly correlated; grouping by uploader stops that correlation crossing a split boundary and inflating metrics.

```py
id_bytes = str(uploader_id).encode("utf-8")
id_hash = hashlib.sha256(id_bytes).hexdigest()
bucket = int(id_hash, 16) % 100
```

Then, for a X/(Y-X)/(100-Y) split (e.g. X=70, Y=85 gives 70/15/15 %):

```py
if   bucket <  X: split = "train"
elif bucket <  Y: split = "val"
else:             split = "test"
```

Grouping by uploader trades split balance for independence. With few contributors the realised proportions will be lumpy. Intend to hand-assign balance until the contributor base is large enough to average out.

#### Additional notes

- EXIF data is stripped on ingest (just used to get date_captured first).
- Versioning: Major = breaking change, category/split/format changes. Minor = new image/annotation data. Patch = corrections to already published data.
- Minting a version and publishing to Zenodo is manual until decided otherwise
- Archives exported to Zenodo cannot be anonymised after download. Such is life.
- /download/vX.Y.Z redirects to Zenodo, versions do not stay on file
- Verifiers who reject can instantly add annotations; make adding an annotation a fast path to rejection.
- Use `argon2-cffi` for passwords
- Use Litestar; it's explicit, implements correct DI, guards, OpenAPI generation, and has SQLAlchemy integration (advanced-alchemy). Plus there's docs
- Use msgspec (Litestar's native serialiser) for payloads; no orjson or Pydantic needed
- Serve files outside the app, from Cloudflare R2 --- images, pyramids, thumbnails, datasets; set `Cache-Control: public, max-age=31536000, immutable` (a full year) on upload. Keys are content-addressed by sha256, so they never change.

#### Deployment

Cloudflare fronts everything; one VPS runs the API, the database and the jobs.

```text
                      ┌──────────── Cloudflare (mitespotter.org) ────────────┐
browser ──HTTPS──▶    │  /api/*   ──▶ Cloudflare Tunnel ──▶ VPS: Litestar      │
                      │  /data/*  ──▶ R2 (custom domain, immutable caching)   │
                      │  /*       ──▶ frontend static assets (wrangler)        │
                      └───────────────────────────────────────────────────────┘
VPS: uvicorn (systemd) · Postgres 16 · cloudflared · systemd timers for jobs
```

- **VPS + Tunnel.** `cloudflared` exposes the API with no inbound ports open. Litestar trusts `CF-Connecting-IP` for the client address.
- **R2 buckets/prefixes.** `images/`, `thumbnails/`, `pyramids/`, `datasets/`. Accessed through R2's S3-compatible API (`boto3`). In dev and tests the same keys live on local disk under `data/` (`MITESPOTTER_STORAGE=local|r2`).
- **On the VPS only.** `originals/` and `backups/` stay on local disk until the weekly job moves them to long-term storage.
- **Frontend.** `mitespotter` is deployed with wrangler as static assets; `/api/*` and `/data/*` are routed before it.
- **Not used, and why.**
  - *D1*: SQLite (no CITEXT, no TIMESTAMPTZ, signed 64-bit integers cannot hold the uint64 `phash`), no psycopg/SQLAlchemy async dialect so no advanced-alchemy or Alembic, no `pg_dump`, 10 GB cap.
  - *Python Workers*: Pyodide only takes pure-Python/Pyodide wheels and Workers have a 128 MB memory limit; ingest needs `rawpy`, `pillow-heif`, `imagecodecs` on 60 MB uploads. Jobs need `pg_dump` and a filesystem.
  - *Hyperdrive*: only useful when Workers talk to Postgres, which they don't.
- **Open question.** Weekly long-term storage on prepaid S3 (VCS bylaw) or R2 Infrequent Access.

#### Scheduled Jobs

Use `systemd`, ensure all configurations are committed, symlink into box from `deploy/`.

**Nightly**

- Backup database via `pg_dump -Fc` (flags say dump as custom format: this is proprietary, compressed by default, and the supports selective and parallel restore)
  - Verify via sandbox (`pg_restore -d test_verification_db -j 4 /path/to/backup.dump`,
    well in python but you get the point)
  - delete last week's backup of this day (should be 7 backups at one time)
- Check integrity before snapshot:
  - No EXIF data in `images/` JPEGs
  - No near-duplicate spanning two splits (pHash)
  - No image in the latest snapshot has changed splits
  - No annotation on a verified image has `is_ai_model` TRUE
  - No annotation on a verified image comes from the verifier user, and no image was verified by its uploader
  - Every verified image has a file in storage and the file's sha256 matches its hash row
  - If any of these fail, assume there is a bug and manual intervention is required (future versions can *maybe* consider a self-healing integrity check, but hard)
-  IF integrity is good THEN snapshot !
  - See [Archive Directory Layout](#archive-directory-layout)
  - Upload the zip to R2 `datasets/`
  - Delete last week's snapshot of this day (keep 7)
- Digest and heartbeat
  - Summarise the day's activity (images ingested, images verified, backlog size, per-split counts), integrity failures, whether a snapshot was written, open report count and age of the oldest
  - Check for orphans in storage --- files not in the database, database rows not on file, and flag them (the latter will have caused an integrity failure)
  - Check disk space usage and remaining space; if below a threshold, raise the alarm
  - Ping healthchecks.io once everything is done

**Weekly**

- Export checkpoint to long-term storage (AWS S3, prepaid as per VCS bylaw, Glacier or Infrequent Access if practical; or R2 Infrequent Access, see [Deployment](#deployment)), including:
  - Nightly database backup (completed just before)
  - Contents of `originals/` (pruning them from box disk)
  - The week's worth of logs (pruning them as well)
- Export originals and backups as individual files, logs as tar.gz; sha256sum to confirm

### Sprint 2: Model

The idea is to get an initial model to pre-annotate the image to act as a utility and save time for labellers. It's important to design this in such a way that **automation bias** is not introduced into the system. A number of factors can help to mitigate this:

- **Source of origin.** Models are registered as users with `is_ai_model = 1`. Since annotations are tied to a user (and remember, you can make annotations without confirming that annotation is complete), the model generates annotations. When a human annotator sees a model's annotation, it's clearly labelled and they are prompted to confirm or delete it. **An image cannot be marked as completed if any of its annotations are a model's and unconfirmed.**
- **Intentional friction.** There cannot be an "Accept all" button, each bounding box must be individually checked. Make human bboxes solid blue and model bboxes dashed viridis-ramp.
- **Test images.** This is more of a diagnostic tool. We should A/B model annotations from the moment they're released to collect data about their effects on annotation quality. We can reintroduce known-verified images as if they weren't and check whether they are re-annotated the same way.
- **Confidence threshold.** This will require some trialling, because the model's confidence is likely to be always low at the start, but exigent confidence thresholds will help to reduce the amount of incorrect annotations that might slip past a human. This should be per-annotation.
- **Human dataset.** This follows from the rule in "source of origin," but model annotations should never enter the published dataset or be used to train the model.
